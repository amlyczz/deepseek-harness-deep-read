# 04 · 真相：会话日志

> 本篇目标：搞懂 DSH 的世界观基石——**会话不是"消息列表"，而是一条只能追加的事件流**。模型看到的历史、屏幕上渲染的对话、磁盘上的文件、token 账单，全部是这条流的不同投影。读完你将能设计出自己的事件词汇表、投影机制和崩溃恢复方案。

## 从一个问题开始

harness 要解决模型的"没有记忆"。天真做法人人都会写：

```ts
const messages: Message[] = []      // 内存里攒
messages.push(userMsg)              // 用时 push
messages.push(assistantReply)
// 崩溃？换台机器？想看历史？想审计？——祝你好运。
```

稍微认真一点的人会存数据库。但存什么？存"对话消息"？马上遇到三个新问题：

1. **视图打架**：UI 想要打字机效果（需要原始 token 流），模型想要压缩后的历史（旧的中间过程该裁掉），遥测想要每个请求的参数快照——一个 `messages` 表装不下这些形态，于是开始建第二张表、第三张表……然后它们开始互相矛盾。
2. **无法审计**："模型为什么这么回答？"——因为它当时看到的上下文和现在 DB 里的不一样了。修改式存储销毁了案发现场。
3. **崩溃丢账**：写一半崩掉，谁也不知道哪半是真的。

DSH 对这三题的答案高度统一，一句话说完：

> **定义一套不可变事件的词汇表，发生什么就追加记录什么（append-only log）；所有需要的形态——模型历史、UI 画面、统计报表——都从这份唯一事实"推导"出来，推导规则本身可被运行时断言校验。**

这就是 UI 工程界熟知的 **Event Sourcing**，DSH 把它贯彻到了字节级。核心实现两处：

- `packages/core/session/src/` —— 内存中的日志与全部投影逻辑
- `packages/session/session-persistence-jsonl/` —— 磁盘落盘

## 事件信封：每条记录长什么样

先看词表的全景——`SessionEventMap` 是一个 TS interface，靠声明合并（declaration merging）让任何插件都能扩展新事件类型（`packages/core/session/src/types.ts:236-337`）。中坚成员一览：

| 事件 | 关键字段 | 记的是什么 |
|---|---|---|
| `turn/start` / `turn/end` | `{turn}` / `{turn, reason}` | 轮次括号 + 结局理由（闭集） |
| `step/start` / `step/end` | `{turn, step}` | 步骤括号 |
| `user/message` | UserMessage（含 source.kind） | 人输入、注入上下文、goal 续轮共用 |
| `assistant/chunk` | `{turn, step, chunk}` | **逐 token 原始流块** |
| `assistant/message` | `{...,usage?, interrupted?}` | 完整助手消息 + 计费同行 |
| `tool/call` | `{callId, name, arguments}` | 模型产出的**原始 JSON 字符串** |
| `tool/result` | `{message, error?, meta?}` | 工具结果 |
| `todo/write` | `{todos}` | 整表快照（仅 UI，永不进模型历史） |
| `request/header` | EpochHeader 快照 | 下一步请求的完整头部（config/system/tools） |

而每个事件的公共信封（`types.ts:408-440`）：

```ts
interface SessionEvent<T> {
  type: T                 // 词汇表里的类型名
  seq: number             // 单调连续序号（见下文，它就是数组下标）
  time: number            // epoch 毫秒
  data: SessionEventMap[T]
  ignorable?: true        // 可忽略标记（前向兼容的关键！）
  surfaceOp?: SurfaceOp              // 仅三类 surface 事件可有：
  sourceEventSeqs?: number[]         // 引用本消息由哪些旧事件构成
}
```

两个精妙之处值得单独说：

**`ignorable` —— 前向兼容的成本核算。** 规则是：读者遇到不认识的事件类型时，若它没标 `ignorable:true` 就必须**拒绝重建整个会话**而不是悄悄跳过。注释讲得很清楚（`types.ts:415-424`）：默认必需意味着开发者忘打标记的后果是"新版程序偶尔拒绝读旧日志"（麻烦），而不是"静默误读了一个语义有分的日志"（灾难）。宁可过度拒绝，不可错误解释——原则三。

**`sourceEventSeqs` —— 因果引用链。** assistant/message 引用构成它的所有 chunk seq；压缩后的替换节点引用被它遮蔽的全部旧节点 seq。有了它，任何派生物都能回溯到自己的原材料。

## append()：入账的五道门卫

```ts
// packages/core/session/src/index.ts:604-655（节选，保留主干）
append(type, data, ...opts): SessionEvent<T> {
  const dataSnapshot = snapshotJsonValue(data)       // 门1：无损 JSON 化+冻结
  if (dataSnapshot === undefined)
    throw new Error(`session event "${type}" carries non-JSON-serializable data`)
  assertSupportedRequestHeader(type, ...)            // 门2：拒绝废弃词形
  const event = Object.freeze({ type, seq: this.log.length, ... })  // 门3：seq=下标
  this.surface.validateNext(event)                   // 门4：预演合法性，失败不产生副作用
  this.log.push(event)                               // 入账
  // 门5：向监听者快照广播 session/event；观察者异常逐个捕获，不影响日志
}
```

五道门的用意依次是：坏数据进不来、老词形冒不进来、序号永远等于下标（这就是"seq 连续性契约"的实现点）、非法序列不留半截、以及**事件一旦 push 即视为提交**——广播发生在事后，观察者出错也无法改变已入账的事实。

`validateNext` 预演的是一组关系不变量：seq 必须严格递增、turn/step 括号必须匹配嵌套、每条 `tool/result` 在同一步内必须有先行 `tool/call`、`todo/write` 这类事件必须闭合在轮次内……违规直接抛错。日志因此不仅在字节上合法，在**结构语法**上也始终合法。

## 投影之一：模型看见什么

这是最重要的一条投影链。概念上分三层：

**第一层：单事件投影规则**（纯函数）：

```
user/message     → 原样成为一条用户消息（刻意不加 <context> 之类的框架包装）
assistant/message → 空内容占位（如纯 max-tokens 计费）→ null，不进历史
tool/result      → 它的消息本体
其他一切          → null
```
(`packages/core/session/src/surface.ts:83-114`)

**第二层：surface = "当前对模型可见的事件集合"。** `SurfaceManager` 维护一个有序 seq 数组 `nodes` 和一个代数计数器 `generation`。大多数事件是追加；唯一的复杂操作是压缩引入的 **replace**：把 `[start..end]` 区段整体替换成一个新节点并递增 generation（`surface.ts:362-379`）。注意措辞——是"从投影中替换"，原始事件在日志里纹丝不动。

**第三层：增量折叠缓存**：

```ts
// index.ts:726-747（节选意译）
deriveMessages(): Message[] {
  if (generation 变了) 全量重建
  else 只投影 nodes.slice(this.derivedNodes)   // 只处理新增节点 → O(增量)
  return [...this.derived]                     // 返回浅拷贝防外部篡改
}
```

循环每次发请求调用的就是它（`agent-loop/src/agent.ts:340-342` 传入 buildRequest）。**历史的权威版本永远现算现取**，没有任何内存缓存会变成第二个真相源。

**黄金法则的断言代码**——上一章预告的运行时不变量，现在看真身：

```ts
// packages/core/agent-loop/src/invariant.ts:39-42
const expected = session.deriveMessages()
if (JSON.stringify(options.messages) !== JSON.stringify(expected))
  fail('... diverges from the dispatch-time durable derivation (log-reconstruction desync)')
```

每次真实请求发出前，把实际 messages 与从日志独立重推的结果逐字节比对；不一致当场失败。除此之外还比对 model/system/tools 等头部必须等于从 `request/header` 事件折叠出的值。"发给模型的 == 日志说的"从一句口号变成了 40 行硬代码。

## 投影之二与三：人类转录与计费

同一份日志还能免费产出另两类视图，且各自有巧妙的取舍：

- **人类转录**（transcript）：只取"append 面"的事件，**过滤掉 replace 替换出来的副本**（`surface.ts:41-55` 有段长注释解释原因：替换是压给模型的，不能让用户看到自己已读过的内容凭空消失或变形）。同一个日志，人看的版本与模型看的版本就此分流；
- **Token 计量**：`token-meter` 包从 durable tail 重放事件折出锚点与表面价格；provider 上报的 usage 只有当其请求头与当前头一致时才作基准，否则整段启发式重估（字符密度估法）。计费不信任单一来源，永远 `max(实测, 估算)` 取保守值。

## 磁盘格式：打包、压缩与崩溃恢复

内存里漂亮还不够，打开 `~/.dsh/sessions/<项目slug>/<sessionId>/session.jsonl[.zstd]`，这才是硬仗。

**布局三招**：

1. **首行头 + 一行一事件**。首行是 `type:'session'` 的 header 行（version/id/cwd/parentSession/seedLength 等）；正文每行一个存储记录。读到未来版本号直接报错让你升级 harness，绝不猜着解析（`format.ts:240-247`）。
2. **chunk 打包行**。逐 token chunk 的信封开销约 56 倍于载荷，于是相邻同类 delta 运行 ≥3 个就打成一行 `text-chunks`（差分编码 seq 与时间戳），实测整日志小约 60%（`jsonl/index.ts:69-75` 注释原文）。开关只影响写字节，读取无条件解包——老日志永远可读。
3. **zstd 分帧**。头帧独立成帧且强制恰一行，让"只读元数据"不用解压全文件。

**崩溃安全的三层功夫**（这个章节信息密度最高，慢慢读）：

- **首次物化用 link() 而非 rename()**（`materializePosix`，`jsonl/index.ts:529-569`）：写临时文件 → fsync 文件 → `link()` 到目标名 → unlink 临时件 → fsync 目录。为什么不用常见的 rename？因为 link 在目标已存在时会失败——两个进程并发物化同一会话时**不可能互相覆盖**，而 rename 会安静地二换一；
- **追加失败回滚截断**：追加后 fsync，一旦写失败就把文件截回追加前的字节数再抛错。注释点明不变量："留半截字节 = 重启后重复的 seq"——宁可丢最后一批，绝不制造重号（`appendLines/rollbackAppend`，651-689 行）;
- **撕裂尾修复**：加载时扫描器记录"最后一个完整换行处"作为提交边界；损坏尾巴延后处置，直到遇见完整 `turn/end` 才定论，尽量少丢数据；修好后再补 fsync 两连击（truncate + 补写恢复事件）（`commitRepair`，431-444 行）。

**与全系统节奏的配合**：热路径 append 零 IO，后台 write-behind 每 200ms 合并批量刷盘；但有两个 fail-closed 闸口（`session-checkpoint-policy/src/index.ts:63-85`）：`llm/stream` 放行前、顶层工具执行前，各自先 `await sessions.flush()`——**模型看到之前、副作用发生之前，前面的账必须已经安全落盘**。刷不动就不干活，原则三再现。

顺带一组对照记忆：同样要原子写，会话日志用 link（多写者防互踩），而 settings/storage 这类"净态小状态"用 rename（单写者 last-write-wins 反而正确）。介质性质决定发布协议，没有银弹。

## fork 与 resume：血统写进 header

- **fork**：`sessions.fork(source, boundary?)` 从既有会话切出一个子会话。boundary 缺省是末事件，但有一个硬约束——切点必须是轮次边缘（源日志 `findLast` 出的最后边界若还是敞开的 `turn/start` 则拒绝，`index.ts:1128-1135`）。子会话 header 写入 `parentSession` 与 `seedLength`，从此血统永久可查；
- **resume**：进程重启后恢复会话时，持久化层会把中断的死账户尾**确定性合成收尾**：没启动的工具调用得到 `TOOL_NOT_STARTED` 错误结果、结局未知的得 `TOOL_OUTCOME_UNKNOWN`，然后补 `step/end` + `interrupted` 版 `turn/end`（`repair.ts:27-133`）。记得第三章说的"interrupted 循环永不自书"吗？它的书写者就是这里。

## 复刻清单

- [ ] 定义你自己的 `SessionEventMap`：≥8 种事件类型 + 信封（type/seq/time/data/ignorable/sourceEventSeqs）；
- [ ] `append()` 五道门卫：JSON 无损校验 → 废弃词形拒绝 → seq=log.length → 结构预演 → 冻结入库后广播；
- [ ] 关系不变量集：seq 连续、括号配对、tool call/result 成对（同一步内）；
- [ ] surface 三件套：nodes 数组、replace 操作、generation 缓存的 O(增量) deriveMessages；
- [ ] 人机双转录分流（human 视图过滤 replace 副本）；
- [ ] JSONL 写路径：临时文件+fsync+link 发布；追加失败回滚截断；撕裂尾扫描与修复；
- [ ] checkpoint 闸口：模型调用前与顶层工具执行前强制 flush。

验收标准：
1. 手工构造一个 tool/result 先于 tool/call 的非法事件序列——append 是否抛错？
2. append 进行到一半 kill -9 进程，重启后加载是否成功且无重复 seq？
3. 在日志里混入一条未知的新事件类型——不带 ignorable 时你的 reader 拒绝了吗？

## 超越思考

- **双重序列化的热路径开销**：deriveMessages 每步全量浅拷贝，不变量还要两次 JSON.stringify 逐字节比——大上下文时可感知。可用世代号/内容哈希做等价判定省掉第二次全文推导。
- **没有迁移故事**：格式版本钉死 0，不兼容直接拒绝；zstd/jsonl 双物理编码互斥还得手工搬运。正式产品需要一个 upgrade-step 链。
- **单进程写者假设**：并发 harness 共享一个 sessions 根目录的场景没有仲裁，多客户端并发写损坏正是社区插件专门修的痛（上游生态已有 session-repair 插件）。
