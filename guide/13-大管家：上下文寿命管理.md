# 13 · 大管家：上下文寿命管理

> 本篇目标：上下文窗口是最贵的硬资源，本篇研究 DSH 的"管家班"怎么让它物尽其用——**spill 在入口限流、token-meter 给全楼装电表、pruner 免费清理、compaction 做最后的事务化搬迁**。读完你将拥有一套完整的上下文寿命管理方案。

## 从一个问题开始

100 轮对话之后会发生什么？系统提示词还在，但历史已经塞满：
- 某次 web_fetch 把整页文档灌了进来（8 万字符）；
- 30 个文件的内容读过就不再重要，却永远躺在历史里；
- 模型开始"忘记"最初的任务定义。

天真的应对是**截断或滑动窗口**——保留最近 N 条。问题是任务定义往往就在最早的几条里，切掉它等于让失忆症患者继续做手术。

DSH 的治理哲学是分层处理、**每层只在必要的层级动刀**：

```
(token 进入历史的旅程)
外部世界 ──▶ [spill 入口限流] ──▶ 历史 ──▶ [pruner 免费瘦身] ──▶ 仍然紧张？
              大文本存仓给预览                中段打点隐形            │
                                                            [compaction 事务化压缩]
                                                            整段折叠成摘要
全部环节共用一块电表：[token-meter] —— 决策依据永远是实测而非感觉
```

## 电表：TokenMeter

一切压力判断的前提是知道当前用了多少。`packages/llm/token-meter/src/index.ts` 的 `measure(session)` 从持久日志尾部折叠出 `{baseline, totalTokens, nodes[]}`。两个诚实设计：

1. **provider 上报的 usage 不被盲信**：只有当那次调用的 canonical 请求头与当前头一致、且总量不低于启发式估值时才作锚点基准——防止换模型/压缩后的陈旧数字污染判断；
2. **永远取保守值** `max(provider实测, 启发式估算)`。启发式就是朴素的字符密度（约 4 字符/token 加结构开销），粗糙但只会高估不会爆窗。

还有个考古功能可作谈资：借助第 04 篇的 `sourceEventSeqs`，它能历史 chunk 重喂进新聚合器来复核当年 provider 报价是否诚实。日志当审计底稿用的又一例。

## 门卫：Spill（入口限流）

与其等巨型文本进了历史再清场，不如在门口安检。`spill-policy` 插件挂在 **post-execute** 前置瀑布（`packages/spill/spill-policy/src/index.ts:190-209`）：纯文本结果超过 `maxInlineBytes` 时——

1. 全文经 `ctx.spillStore.saveText` 存入会话私有的泄流仓库；
2. 按 head/tail **双端预算**生成预览（头部保开头、尾部保结尾），并精确预留提示行的字节，恒不超上限；
3. 产出的替换文本 = 预览 + 定位器 + 取回指引。模型如果确实需要全文，照着指引去取（需要时再 spill回来一份小的），而不是被塞一整页；
4. 两条纪律收尾：跳过 `read` 工具防"读→spill→再读"循环；spill 自身失败一律 best-effort 保内联，注释原文*"A spill failure must NEVER …"*——管家的失误绝不能把成功调用变成错误。

会话 fork 有个配套细节：spill 工件不复制，新泄流归子会话——血统清晰不背历史包袱。

## 清洁工：Pruner（免模型的瘦身）

压力未到压缩阈值时先试试免费手段。tool-result pruner 对每个超尺寸的 `tool/result` 做**中段打点**：Unicode 码点头尾各留一段、中间替换成 `PRUNE_MARKER` 标记（`compaction-tool-result-pruner/src/index.ts:83-122`），然后以 surface 替换操作落地并追加影子计价事件。0 次 LLM 调用，先榨一遍水分，测完价再看够不够。

## 大手术：Compaction（事务化压缩）

真正的压轴。目标：把"很久以前"的历史区间折叠成一份摘要消息，同时保证崩溃时不变坏。

### 触发时机：三条路

| 触发 | 场景 | 特殊之处 |
|---|---|---|
| 步间检查 | pre-step 时观测到 ≥80% 窗口 | 默认 `thresholdRatio=0.8` |
| 溢出恢复 | 上游报 CONTEXT_WINDOW_EXCEEDED | 无视阈值强制压一次，成功后返回 retry（计入重试上限） |
| 手动 `/compact` | 用户命令 | 包在 runMaintenance 里执行 |

### 选区：从尾巴往回数

`selectCompactableRange`（`region.ts:98-134`）：从最新事件反向累计价格直到攒够 `retainRatio`（默认 16%）预算 → 得到**保留起点**；再向前回退到工具配对平衡处切口——按表面序折叠 in-progress 的 tool-call 数，确保切口两侧配对平衡（`tool-pairing.ts:117-131`）。绝对不能把一个 tool/call 切得和它的 result 天人永隔：那会让下一次请求直接违反协议。

### 事务协议：八拍

```
① compaction/start        ← 作为锁入账（owner 字段判无主/有主）
② 准备定价快照 + 回放输入
③ 异步 summarize          ← 默认实现妙极了：ctx.llm.stream() 复用对话自身的
                            system/tools/消息前缀 —— 保住供应商 KV cache，
                            压缩调用本身就是一次顺手的缓存命中
④ 尺寸裁决                 ← 摘要必须比被遮蔽内容更小，否则拒绝提交！
⑤ 稳定性复核               ← whole-surface 或 selected-span 两规则确认期间没变化
⑥ 同步提交 compaction/summary ＋ 一条带 {op:'replace'} 的 user/message
   （sourceEventSeqs 同时援引 start、summary 与全部被遮蔽节点 —— 因果链完整）
⑦ compaction/end           ← 解锁
⑧ 任一步失败 → 恰好补一条带 error 的 end；中途崩掉的留下可侦测的孤儿 start
```

第④拍值得划重点：**摘要不比原文小就整体放弃**。听起来像白干，实际是防退化保证——不能接受"花了钱压缩，结果上下文反而变长"。

### 保什么：结构化交接清单

最近 retainTokens 预算的尾部原封不动；被遮蔽区间化身一条**固定结构的检查点消息**（`summarizer.ts:26-58`）：Primary Request / Key Concepts / Files and Code / Errors and Fixes / Pending Jobs / Current Work / Next Step / Critical Context 八个章节外加一段前言。两处小心思显出成熟度：

- 章节 prompt 里内置**代际合并指令**——防止摘要层层转发时不断复制旧摘要导致滚雪球；
- 这一切只是投影层替换。原始事件仍然完好躺在日志里（第 04 篇早就说过），人视图还能查到全部原始细节。**模型的现在被压缩了，系统的过去从未丢失。**

## 四件套合奏

一次典型的深夜长任务时间线：

```
web_fetch 返回 200KB ──▶ spill 门口拦截，入库给预览           （0 成本）
40 轮过去了，grep 结果们开始臃肿 ──▶ pruner 中段打点免费清一波  （0 LLM 调用）
预检压力 81%>80% ──▶ compaction 八拍事务，老历史折叠成交接清单 （1 次 LLM 调用，KV cache 友好）
上溢黑天鹅来了 CONTEXT_WINDOW_EXCEEDED ──▶ 强制压缩+retry 通道 （保命路径）
全程每个决策基于 token-meter 的保守实测                        （电表常开）
```

## 三原则对账

- **原则一**：压缩只动投影不动日志；摘要的 sourceEventSeqs 让一切可回溯；所有计价是日志的折叠；
- **原则二**：四个角色全是挂在 seam/post-execute/pre-step 上的普通插件，可以单独换成你的实现（比如接向量库做选区）；
- **原则三**：不缩就不提交；孤儿锁可侦测；usage 不达标不当锚点；fail-closed 溢出通道。

## 复刻清单

- [ ] TokenMeter：日志折叠 + 锚点资格判定 + 密度估算兜底；
- [ ] Spill：预算式双端预览（含预留字节计算）+ 泄流存储 + 失败保内联；
- [ ] Pruner：码点头尾保留 + 影子计价事件 + surface 替换；
- [ ] Compaction 事务：锁事件/尺寸裁决/稳定性复核/八拍闭环/孤儿检测；
- [ ] 切口算法：retain 起点反推 + 工具配对平衡回退。

验收标准：
1. 人为构造一个摘要比原文大的 summarize 结果——事务是否拒绝提交？
2. 在压缩进行中 kill -9——重启后是否能看到那个孤儿 start 并能安全接管/报告？
3. 把切口故意移到一个 open tool-call 后面——配对平衡检查是否拦下？

## 超越思考

- **连续区间的局限**：现在的选区是物理连续段。语义聚类选区（按话题向量分组折叠）技术上已可行，难点在保持日志因果引用完整——这是一个真正开放的问题；
- **外挂记忆的正确姿势**：想把删掉的内容找回来？不要造第二真相源——做一个"检索即注入"的插件：查询走工具、命中作为 inject 进上下文、行为全部天然入账。原则一之下，记忆系统应该是投影的投影；
- **KV cache 经济学**：默认 summarizer 已经贴着缓存友好设计。更进一步可以在 pre-step 层面做"前缀稳定性规划"——把易变的动态 section 往后挪，量化每次请求省下的 cacheWriteTokens，这可能是最便宜的 token 成本优化。
