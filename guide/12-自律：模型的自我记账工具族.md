# 12 · 自律：模型的自我记账工具族

> 本篇目标：研究五件看似平凡的模型工具——todo、goal、plan、jobs、schedule。它们表面五花八门，底下却是**同一个设计模式**的五次重复：追加式快照事件 + 纯折叠投影 +（必要时）硬封顶。掌握这个模式，你不仅能复刻这五件，还能自己发明第六件第七件。

## 从一个问题开始

模型有三个与生俱来的缺陷，harness 必须用机制（而不是提示词恳求）来对冲：

| 缺陷 | 后果 | 机制的回答 |
|---|---|---|
| **健忘** | 长任务中途忘记要做哪几步了 | todo |
| **无恒心** | 用户离开后它就"下班"了，目标烂尾 | goal / schedule |
| **无法无天** | 说好的先规划再动手，三句话后就开始改代码 | plan mode |

外加一个 harness 自身的需要：

- **慢操作**不该阻塞一次工具调用直到超时 → jobs

下面逐个拆解，注意观察它们惊人的结构同源性。

## todo_write：一份自己维护的便签

多步工作需要的不是"提醒"，是一份**模型自维护、人类可窥视**的结构化清单。DSH 的实现教科书级简练：

- 工具语义是**整表替换**——描述文案第一句就是"发送整个列表，没有部分更新"。为什么不做增量更新？因为增量意味着 merge 冲突的可能；整表替换让"记录的快照 = 模型以为写的"，`additionalProperties:false` 从 schema 层面封死自由发挥；
- 每次调用 append 一条 `todo/write {todos}` 日志事件，last-write-wins；回放即得全史；
- 默认约束**至多一个 `in_progress`**（配置 `allowParallelInProgress` 可开并行），连工具描述文案都随配置切换——schema、约束、说明三位一体；
- UI 渲染的投影规则同样三行讲完：`todo/write` 覆盖状态、`turn/start` 清空新板、`turn/end` 保留已完成项供回顾。

## goal：跨轮次的目标台账

goal 解决"用户给了个大目标然后去睡觉"的场景。数据结构两样东西就够：

1. **阶段闭集** `active | paused | blocked | complete`——注意 blocked 是唯一的"因问题而停"，强制携带路由用的 code 与人机双读 message。"卡住了但说不出为什么"是不允许存在的状态；
2. **变更事件** `goal/change`：非 clear 是变后全快照（含 revision 与 roundsStarted 计数），clear 是墓碑事件。

真正体现设计强度的是**续轮协议**：每次为延续目标而获准的轮次，其 user message 必须携带 `{goalId, revision, round}` 三元组；而**回放侧会拒绝编号缺口、拒绝陈旧 revision、拒绝已停止阶段、拒绝超过 maxGoalRounds 的轮次**。翻译一下：想无限循环刷目标？日志的语法检查这道闸先过不去。防失控不靠 AI 良知靠格式校验——又是原则三。

## plan mode：把"先规划"做成日志态

plan mode 最容易被做砸成一句系统提示词。DSH 把它彻底机制化了：

- 状态存于持久事件 `plan/mode`（last-one-wins）——重启、fork、另一个标签页全都天然恢复，无内存镜像；
- pending 切换由 pre-step 监听在本步获准后落盘（pending 是纯回放量！）；
- 一个反直觉的设计：`exit_plan_mode` 工具**常驻注册**——进出模式只增删提示词 section，从不改工具目录。为什么？"运行中突然出现/消失一个工具"会让模型的 tool 心智模型紊乱，也给 schema 缓存制造麻烦；
- 提交计划必须带 markdown 完整方案，然后走 ask-user 复核（intent 'plan-review' 让 Web 渲染专用决策卡）。两个善意的细节：用户直接关掉评审框不算失败而是"抢回了话头"；选 keep planning 时反馈文字以 error 形式回流——模型对负反馈的反应远比对礼貌的建议敏感。

## jobs：后台运行的通用外壳

bash 一跑 10 分钟、subagent 后台慢慢爬，都需要"转后台"。jobs 运行时的生产者契约值得整段背下来：

```
JobStart { kind, label, owner?, run() }
· 运行时先 preflight 再 run —— 之后不再做可能失败的步骤
· owner 是访问围栏（按会话）；agent 释放时它的 jobs 连带走
· cancel 同步幂等；done 在"资源已释放之后"才 resolve（不只是活干完）
· readOutput 用单游标区分流式输出与终末输出
```

对外三个查询工具 job_output/list/output；并发上限超限时错误文案直接指路"用 job_kill 释放后再试"——错误消息当文档写。

最精巧的是**完成通知的自激熔断**：job 完成时若 owner 正忙，以 inject 投进下一步（不唤醒）；若空闲则唤醒开新轮。危险在哪？被叫醒的 turn 可能启动新 job → 又被叫醒……为切断这条自我激励链，连续自动唤醒上限 `maxConsecutiveWakes=3`，超出降级为注入，仅用户真实输入才重置计数。一个三行代码的计数器，防住了一类无限烧钱故障。

## schedule：给模型一根计时器

模型的宇宙里没有时间流逝感。schedule 补上：三种持久规则——延时 after_seconds、绝对 at、周期 every_seconds（≥300s 且锚定创建时刻防漂移），统一规范化成显式四位年份 RFC3339 UTC 的 scheduledAt 存储。

交付方式体现了全书级别的克制：**到期就是把一句话 followup 回原会话**，成为普通 FIFO 新轮——没有新的通知通道、没有回调框架、"投递即完成"零回执边界。丢提醒的兜底是重启时对过期记录一次性补投。318 行附近起的三件套工具 schedule_create/list/delete 全部围绕这套持久规则转。

## 五个一模一样的答案

| 子系统 | 快照事件 | 投影 | 硬闸 |
|---|---|---|---|
| todo | `todo/write` 整表 | 回放 last-write-wins | schema 封死；≤1 in_progress |
| goal | `goal/change` 快照/墓碑 | 阶段折叠 | round 编号连续性+revision+maxRounds |
| plan | `plan/mode` LWW | pending 纯回放 | 常驻工具不冷切换 |
| jobs | 终态事件 | 快照投影 | 并发上限；自激熔断 ≤3 |
| schedule | 规则记录 | 到期扫描 | ≥300s；显式年份时区 |

**模式公式**：凡是"模型的自我状态"，都收敛为 *append-only 快照事件 + 消费方各自折叠 + 格式层硬性边界*。没有任何一个用了独立的存储引擎或全局变量。下次你想加"agent 的记忆卡片""待办星级""每日复盘"，照这个公式套就行。

## 三原则对账

本章几乎不需要解释——五个子系统全身上下都是三条原则的原教旨执行。

## 复刻清单

- [ ] todo_write 整表替换 + 严格 schema + 计数返回值；
- [ ] goal 台账：四相闭集 + blocked 强制 code/message + 三元组续轮协议 + 回放四重拒绝；
- [ ] plan mode：日志态 + pre-step 落盘 + 常驻 exit 工具 + ask-user 富复核；
- [ ] jobs 外壳：preflight-before-run / owner 围栏 / 幂等 cancel / done-after-release；
- [ ] 自激熔断计数器；
- [ ] schedule：规范化 RFC3339 + followup 即投递 + 重启补投。

验收标准：
1. 手工伪造一条 round 断档的 goal 续轮消息入回放器——是否被拒？
2. 连启 5 个秒完 job 而无人干预——第 4 个之后是否还能触发 wake？（应该已被熔断）
3. 系统时钟快进 25 小时，every_seconds=86400 的定时是否仍准点而非累积漂移？

## 超越思考

- **记账还全是单代理视角**：多个 agent 共享一张 todo 板、board 级 CAS 在实验团队包里已有雏形，产品化是明显机会；
- **goal 的验收自动化**：round 协议解决了"无限循环"，还没解决"何时算成功"——接一套可执行的 acceptance criteria（命令 + 预期断言）能让 complete 从自评变成实证。
