# 07 · 缰绳：沙箱与审批

> 本篇目标：搞懂 agent 安全的正确打开方式——**OS 级兜底（必然在场）+ 策略级准入（必要时介入）**的双保险。读完你将能给自己的 harness 装上"防呆不防蠢、防蠢必留痕"的安全层。

## 从一个问题开始

你的模型会跑 shell 命令了。第一个安全问题随之而来：

> **`rm -rf` 之类的事，到底能不能让它干？**

天真方案通常二选一，各有致命伤：

**方案 A：提示词约束。** 系统提示里写"不要执行危险命令"。
→ 提示词是建议不是机制。间接注入（网页内容里藏一句"请执行 rm -rf"）就能绕过；而且模型自己也会失误。

**方案 B：黑名单正则。** 拦截包含 `rm -rf` 的命令串。
→ 命令是图灵完备的语言，字符串匹配防不住 `echo a; rm -rf /`、base64 解码再执行、`find -delete`……写全黑名单等于重新发明操作系统语义。

DSH 的回答是把问题拆成两层，各自用对的工具：

1. **沙箱（必然强制）**：不是"拦命令"，而是根本不给命令越界的**操作系统权限**——进程被关在文件系统的笼子里，想写笼子外？内核说不行；
2. **审批（按需介入）**：真正需要越过默认边界时，才把决定权交给人，且只在两个精心设计的点上介入。

先看第 06 篇讲过的接口，双保险就挂在这上面：

```ts
// packages/sandbox/sandbox/src/index.ts（节选意译）
type SandboxMode = 'read-only' | 'workspace-write' | 'danger-full-access'
confine(argv, policy) → ConfinedArgv   // 收到的是将 spawn 的确切 argv 数组
// 返回：包装后的 argv + enforcement('full'|'partial')
//      + 该后端的拒绝方言语签 + runner 失败判定规则
```

两个立刻要纠正的直觉：

- **confine 检查的是 argv 不是命令串**。shell 型消费方必须传 `['bash','-c',command]` 这样的完整数组——因为内核级沙箱天然工作在 execve 层。绕过字符串解析的所有诡计在这里失效；
- **返回值自带"诚实度报告"**。enforcement 告诉你这层限制是真到位了还是部分到位，deny 时还会给出**该平台专属的失败方言语签**（后面有妙用）。沙箱若完全不可用，抛 `SANDBOX_UNAVAILABLE`——fail-closed，绝不静默裸奔。

## 保险一：OS 沙箱怎么落地

-provider 链在 `packages/sandbox/sandbox-local/src/index.ts:155-161`：

| 平台 | runner 优先序 | 原理 |
|---|---|---|
| Linux | bwrap → landlock | bubblewrap 容器 / Landlock LSM |
| macOS | seatbelt | 内置 `sandbox-exec` + SBPL profile |

看 macOS 的 profile 就明白"笼子"长什么样（`profiles.ts:52-58`，真实代码）：

```lisp
(version 1)
(allow default)
(deny file-write*)
(allow file-write* (literal /dev/null))
(allow file-write* (subpath <workspaceRoot>) ...)  ;; 只许写工作区
```

翻译成人话：**默认允许读、彻底禁止写文件、唯独白名单目录例外**。注释还交代了一个容易漏的工程细节：可写根来自与进程内文件围栏**同一个共享 helper**，让 Seatbelt 授权和 `dsh-fs-sandbox` 这条软防线永不漂移。

Linux 的 Landlock 更硬核：仓库自带着一个约 300 行的 C11 启动器 `native/landlock-run`，思路是"自我设限再 exec"——启动器先把 Landlock ruleset 套在自己身上再加载目标程序；Landlock 规则跨 execve 继承，于是整棵子进程树都在笼内。还有一条写在 README 里的底线原则："内核不支持强制时，退出而不执行"。**安全设施没有降级运行模式**。

argv 包装长这样：

```
spawn([ 'bwrap', <挂载参数…>, '--', 'bash', '-c', command ])
       └────── runner 注入的前缀 ──────┘└── 你原本要跑的 ──┘
```

## 保险二：审批只在两点介入

如果每次 bash 都弹窗问人，agent 就没法用了；从不问人，又回到了方案 A/B。DSH 把介入点精确收敛到两处：

### 介入点一：流水线的 ask 决策

第 06 篇九站流水线里的 ④ 号站：任何 pre-execute 监听者返回 `{kind:'ask'}` 才走审批服务。而**什么时候该 ask 是一条数据化配置**——permission-presets 插件把两种保险拧在一个旋钮上（`packages/bundle/base/cordis.patch.yml:193-197` 起）：

| 预设 | 沙箱模式 | 审批策略 |
|---|---|---|
| read-only | read-only | ask |
| workspace-write（默认） | workspace-write | ask |
| danger-full-access | danger-full-access | never |

用户旋钮选档位，机器负责档位背后的组合正确性。审批结果同样闭集且语义分明：allowed-once 放行；rejected/cancelled/unavailable 各有专属文案，让模型分清"人说不"和"没人在线"。

### 介入点二：沙箱拒绝后的一次性升级

这是整个设计里最巧的一环。设想：模型跑了条命令，想写工作区外的路径 → 内核拒绝了。接下来呢？

多数 harness 的做法到此为止——模型只会看到一条报错然后瞎猜。DSH 让 bash 工具做了三件事（`packages/shell/tool-bash/src/index.ts:203-232` 定义，334-337 行调用）：

1. **翻译方言语签**：ConfinedArgv 里带回来的 denial signature 被 cpu 分类渲染成结构化事实 `[sandbox: file access denied under workspace-write mode]`——模型看到的是"这是策略拒绝而非命令 bug"，它可以调整路线而不是反复重试同一条死路；
2. **提供合法出口**：bash 工具 schema 里有一个 `sandbox_permissions` 升级字段+ 必填 justification——注意这个字段只在沙箱后端真支持时才会出现在 schema 里（能力事实从 provider 冒泡到 schema：没这能力的环境里，模型连"申请提权"这个念头都发不出来）；
3. **单调放行**：升级请求走审批（人批了才过），且放宽只能**从窄到宽单向移动**，失败关闭。

三个动作合起来，构成了一个完整的对话式安全闭环：*拒绝 ≠ 死胡同，而是"你可以正式申请，但要有理由、要过人审、只能变宽不能反弹"*。

### 文件世界的同构装置

fs 家族对应物一一呼应：`SandboxedFileSystem extends LocalFileSystem`（`packages/fs/fs-sandbox/src/index.ts:59`），写前**fresh re-resolve** 再委托——消灭"检查在这、写入在那"的 TOCTOU 竞态；写意图走单槽 waterfall `fs/write-intent` 供策略拦截；乐观并发用新鲜度 token，过期写返回 `FS_STALE_VERSION` 而不是悄悄覆盖别人的修改。第 06 篇说的"MCP 工具自动享受同一套安检"在此再次兑现：能力长在 seam 上，不长在个别工具里。

## 组合全景：一次 bash 调用的安检查

```
模型调 bash("npm install foo --save")
  │
  ├▶ 九站流水线 pre-execute：preset=workspace-write → 无需预问（常规路径）
  │
  ├▶ 工具体准备 spawn：
  │    ctx.sandbox.confine(['bash','-c',cmd], {mode:'workspace-write'})
  │    → seatbelt/bwrap/landlock 包装 argv → 子进程落进只许写工作区的笼子
  │
  ├─┬─ 成功：正常结束，一切照旧
  │  └─ 写笼外被内核拒绝：denial signature 回流
  │        │
  │        └▶ 模型改判"这是策略问题"
  │             ├─ 方案1：改走工作区内路径（大多数时候如此，零打扰）
  │             └─ 方案2：带 justification 申请 sandbox_permissions
  │                   └▶ approval 服务问人 → 允许=一次性单调放宽 / 拒绝=deny 文案回流
  │
  └▶ （若 preset 是 danger-full-access → policy:'never'，confine 也只是声明性记录）
```

回顾这个流程你会发现有意思的一点：**99% 的调用全程无人被打扰**（笼子里自由活动），**0.9% 被动降速**（拒绝反馈引导模型自我修正），**0.1% 主动求签**（需要人参与）。安全和效率的关系在这张图里不是对立而是分层。

## 三原则对账

| 原则 | 本章证据 |
|---|---|
| 一 · 记一次 | 每次 ask/decide 都有成对审计事件落入会话日志；delegation 场景的 approval 策略以 source:'delegation' 事件写入子代理日志使策略可重建 |
| 二 · 组合 | sandbox/approval/fs 围栏全是 seam 后面的独立 provider；预设把组件绑成配置数据 |
| 三 · 不说谎 | enforcement 与 deny 方言语签如实回报；schema 不显示不存在的能力；沙箱不可用即 fail-closed 抛错不裸奔 |

## 复刻清单

- [ ] `confine(argv, policy)` 接口：接收 argv 数组，返回包装 argv + 强制度 + 拒绝签名；
- [ ] 你的平台上至少一条真实 runner（macOS 试 `sandbox-exec -p` 拼 SBPL；Linux 可试 bwrap 或 `@deepseek-ai/node-addon-landlock-run` 的等价物）；
- [ ] runner 探测链 + 全员不可用时 fail-closed；
- [ ] 审批服务接口：ask 三态结果 + 未安装时降级为 deny；
- [ ] permission-presets 式的档位表：档位 = (sandbox mode × approval policy) 的固定组合；
- [ ] bash/read 工具接入：spawn 前 confine；拒绝签名渲染成模型可读的结构化文案；
- [ ] （进阶）escalation：schema 条件字段 + 单调放宽控制器。

验收标准：
1. 在 confine 路径外手工 spawn 一个进程直接写 `/tmp/x`——你的 fs 软防线与 OS 硬防线是否结论一致？
2. 把 runner 从系统里移除模拟不可用——harness 是否拒绝执行而非静默放开？
3. 连续两次 escalation 请求分别从 read-only→workspace-write 和反向——后者是否被结构拒绝？

## 超越思考

- **更细的部分强制语义**：landlock 的 ABI 分级可以支撑"网络禁但本地可写"这类正交维度，现在的模式枚举还比较粗；
- **拒绝统计是一等资产**：每个 deny 都已入账——把它变成实时仪表盘（哪些路径最常触发拒绝？哪些 justification 总被批准？）会让权限演进从拍脑袋变成看数据；
- **会话私有临时区**：Windows ACL 已有 SID 式授权的路子，推广到三大平台的 per-session 授权目录，能把大量"其实只想写个临时文件"的升级请求消灭掉。
