# 02 · 全景：一条消息的一生

> 本篇目标：在你深入任何一行代码之前，先跟着一条真实的用户消息，**从屏幕上的键盘敲击，到模型的 HTTP 请求，到工具真正执行，再到 token 变成像素**——完整走一遍。这一遍是"快进的电影"，看不清的每一站都会标注它属于后面哪一篇。读完本篇，你对 DSH 的全局地图就建立起来了。

## 从一个问题开始

第 01 篇我们说 harness 要给模型装上手脚、记忆、感官和刹车。但把这四样东西装上去之后，一个立刻会出现的问题是：

> **这些东西分布在几十个包、几万行代码里，它们怎么协作？当用户发来一句话，信息的洪流到底流经哪些关口？**

这就是本篇要回答的。我们先给出总地图，再沿地图走一遍全程。

## 全局地图：四个平面

DSH 整个系统可以看成四个平面（plane）。记住这张图，全书 15 篇都是在放大它的某一块：

```
┌─────────────────────────────────────────────────────────────┐
│  交互平面：浏览器前端 (apps/web, packages/client/*)             │
│     React 组件 ← 插件化渲染器 ← seq 对账窗口 ← WS 下行通道       │
└──────────────────────────┬──────────────────────────────────┘
                           │ /api/* RPC + downlink WebSocket
┌──────────────────────────▼──────────────────────────────────┐
│  智能平面：agent 世界 (packages/core/*)                        │
│                                                              │
│   Agent 循环(03) ──读──▶ 会话日志(04) ──投影──▶ 模型历史        │
│       │ 发请求                                    ▲          │
│       ▼                                          │ 组装       │
│   LLM 适配层(05) ──HTTP/SSE──▶ 大模型 API          │           │
│       │ 返回 tool-call                           │           │
│       ▼                                          │           │
│   工具流水线(06) ──安检──▶ 工具体(read/write/bash…) │           │
│                    ▲        │                  │            │
│              审批/沙箱(07)    │ 每一步都落日志     │            │
└──────────────────────────┬──────────────────────────────────┘
                           │ 提供 ctx.fs / ctx.subprocess 等
┌──────────────────────────▼──────────────────────────────────┐
│  能力平面：真实世界                                           │
│  (packages/fs|shell|sandbox|subprocess|mcp...)               │
│     本地磁盘 · 子进程 · Landlock/Seatbelt 沙箱 · 网络 · MCP    │
└─────────────────────────────────────────────────────────────┘

（垂直贯穿所有平面）：骨架平面 —— Cordis 插件树 (08) + 启动组装 (09)
```

再看一眼这张图会发现，连接一切的介质是**事件**。DSH 的官方架构文档把事件分成三个域——这三个词后面每一篇都在用，现在必须认识：

| 事件域 | 是什么 | 特点 | 例子 |
|---|---|---|---|
| **会话事件** | append-only 日志里的持久事实 | **重启后依然存在**；一切视图从它推导 | `user/message`、`assistant/chunk`、`tool/call` |
| **Agent 事件** | 活跃 agent 身上的实时通知 | 进程内广播，不持久化 | `agent/pre-step`、`agent/request` |
| **能力事件** | 挂在某个能力接缝（seam）上的策略钩子 | 谁监听谁生效 | `fs/write-intent`、`tools/post-execute` |

一句话记忆：**会话事件是"发生了什么"的法律记录，Agent 事件是"正在做什么"的实时电台，能力事件是"谁想干什么先过我这关"的检查站。**

## 主线：一次对话的十九站

场景：你在 Web UI 里输入 *"帮我跑一下测试"* 并回车。下面是从敲下回车到看见回答的全部驿站。

### 上行：从像素到循环

```
[1] 浏览器输入框 → 命令检查
    输入若以 "/" 开头且命中用户命令（如 /compact），直接分派执行，
    不惊动模型。(→12篇)

[2] POST /api/session.prompt
    普通消息走 HTTP RPC 到本地服务器：
      { type:'client-request', rpcId:<uuid>, method:'session.prompt',
        payload:{ sessionId, mode:'queue'|'steer', content, clientTimeZone } }
    rpcId 由前端铸造、响应原样带回——这是全系统统一的对账信封。(→10篇)

[3] 图片预入库 + 时区校验
    服务端先把 base64 图片存进附件库换成持久引用，校验 IANA 时区，
    然后构造标准 user/message：
      source: { kind:'user', rpcId, clientTimeZone }
    注意"请求身份"被永久写进了消息本身——审计从此开始。(→04篇)

[4] 投进收件箱：followup() 还是 steer()？
    mode='queue' → agent.followup(msg)：排进下一轮队列；
    mode='steer' → agent.steer(msg)：插队进当前步骤。
    两者在代码里只差两个参数，语义天壤之别。(→03篇)

[5] 驱动器醒来
    若 agent 正空闲（idle）且收到的是唤醒消息 → 启动驱动器；
    若正在忙，唤醒消息改道下一轮队列安静等候。
```

### 中段：循环与模型的往返

```
[6] turn/start 先记账
    循环做的第一件事是把"我要开一轮了"写进日志——
    记账永远发生在干活之前。(→03、04篇)

[7] preStep：领工作 + 组装弹药
    a. inbox.claim()：原子取走全部到期输入；
    b. systemPrompt.assemble()：收集各插件注册的提示词片段与工具清单；
    c. 广播 waterfall 事件 agent/pre-step：任何插件可改写或拒绝这批
       输入（上下文压缩就是在这里给历史瘦身的）。(→13篇)

[8] step/start + user/message 落库 + 请求构造
    buildRequest()：从日志推导模型历史 deriveMessages()，
    再过一道 agent/request waterfall（插件可换模型/调参数），
    最后整个请求深度冻结。
    黄金法则此刻登场：发给模型的历史 = 从日志重推的历史，
    运行时有不变量逐字节断言。(→04篇)

[9] llm/stream 出口
    一个 waterfall 让拦截者（如持久化检查点）可以先刷盘再放行，
    最终到达适配器：DeepSeek 直连适配器拼好 HTTP 头，
    POST ${baseURL}/chat/completions，accept: text/event-stream。(→05篇)

[10] SSE 字节流 → StreamChunk 中立词汇
     适配器把供应商方言翻译成统一词汇：
     text-delta / reasoning-delta / tool-call-delta / usage / finish ……
     每个 chunk 一到，循环立即干两件事：
       ① 原样 append 为日志事件 assistant/chunk（保真回放的根基）
       ② 喂给共享聚合器 BlockAssembler 拼装成块。(→04、05篇)

[11] assistant/message 收束
     流结束，聚合出完整助手消息连 token 用量一起落库，
     并用 sourceEventSeqs 反向引用全部原始 chunk 的序号。
```

### 中场：工具真正动手

```
[12] 模型说要调工具 → 九站执行流水线
     冻结参数 → tools/pre-execute（许可决策 allow/deny/ask）
     → ask 则弹审批（人说不=deny，没渠道也=deny）→ 单调守卫复查
     → tools/execute 环绕层（超时策略住这里）→ 真正的工具体
     → 结果按 output schema 校验并渲染 → tools/post-execute
     （spill 在这里截胡超大输出）→ finalize + 冻结广播。(→06、07、13篇)

[13] 工具体伸手向能力平面
     以 bash 为例：sandbox.confine(['bash','-c',cmd]) 把命令包进
     Landlock/Seatbelt 的 argv 前缀再 spawn 子进程；
     以 read/write 为例：经 ctx.fs 的 provider（本地磁盘或远程沙箱皆可换）。(→07篇)

[14] 双事件闭环
     tool/call（模型的原始 JSON 参数串）与 tool/result（带 meta 与错误结构）
     相继落库；UI 靠这两个事件画出工具卡片。(→04篇)

[15] 还欠活吗？
     有工具调用 = 模型欠了一轮回应 → 回到 [7] 开新步骤；
     无工具调用且收件箱空了 → 广播 serial 事件 agent/turn-stopping
     （有监听者在此刻补投消息），然后机器重新数一遍收件箱——
     数据说了算，不听监听者的口头承诺。
```

### 下行：从事实到像素

```
[16] 服务器广播 session/event
     日志每一次追加都实时广播；api-proxy 给工具类事件现算一份
     ToolEventView 渲染提示，打包进下行 WebSocket 帧。（注意：
     线上传输的是裸事实+渲染提示，前端不存任何二手状态。）(→10篇)

[17] 前端 seq 对账窗口
     SessionManager 按 seq 维护连续窗口：乱序丢弃、缺口拉历史页缝补；
     事件流随后交给一组声明式状态机 ConversationNodeDefinition 折叠——
     "step/start 开节点、chunk 更新节点、message 定稿节点"。(→10篇)

[18] keyed 座位渲染
     ChatView 给每个节点一个独立订阅的座位（兄弟更新互不打扰），
     按 node.kind 分发给注册好的 renderer；
     markdown 用增量解析器——冻结前缀、只重解最后两块，
     流式渲染从 O(n²) 降到 O(1)。token 变成了你眼前的文字。(→10篇)

[19] turn/end completed，状态翻回 idle
     最后一条持久事件写下本轮结局与理由；
     死掉的只是这轮工作，agent 与 harness 都活着等下一句话。
```

| 驿站 | 平面 | 关键角色 | 深入篇章 |
|---|---|---|---|
| 1-2 | 交互 | composer、RPC 信封 | 10 |
| 3-5 | 智能 | api-proxy、inbox | 03、04 |
| 6-8 | 智能 | driver、assemble、冻结请求 | 03、04 |
| 9-11 | 智能+外部 | LLM 适配器、SSE、聚合器 | 05 |
| 12-14 | 智能+能力 | 流水线、审批、沙箱、工具体 | 06、07 |
| 15 | 智能 | turn-stopping、数据裁决 | 03 |
| 16-18 | 交互 | 广播、seq 窗口、折叠状态机、增量渲染 | 10 |

支撑这一切成立的两条暗线：让所有组件可插拔的 Cordis 骨架（08）、决定你运行的到底是哪个组合的启动发行链路（09）。另外还有一群藏在幕后的"认知增强"角色——subagent、todo、压缩、技能目录——它们在第 11-13 篇才登场，但你在上面已经瞥见了它们的影子（pre-step 里的压缩、post-execute 里的 spill）。

## 三份"账本"：同一轮对话的三种形态

走完全程回头看，系统里其实存在三份彼此关联的账本，**内容同源、形态不同**：

1. **持久日志**（磁盘上打包压缩的 JSONL）：一条不落的全部事实，包括逐 token 的 chunk——崩溃后靠它无损恢复；
2. **模型历史**：日志的一个投影，会被压缩替换操作改写形态（旧事实仍在日志里，只是从投影中隐去）；
3. **屏幕画面**：日志的第三个投影（窗口内的连续区间 + 折叠后的节点树），断线重连后按 seq 缝合重建。

这正是导读三原则中的第一条："事实只记录一次，其余皆投影"。第二条你已经见到——消息流经的每个关口都是注册出来的插件行为，没有一处硬编码。第三条也无处不在：rpcId 对账、seq 连续性断言、"usage 必须在 finish 之前"的流协议契约……宁可报错，不带病运行。

## 自己动眼看一遍

纸上得来终觉浅。两个五分钟实验推荐给你：

**实验 A：看活的配置树**

```sh
npx @deepseek-ai/dsh --profile web --dump-config > tree.yaml
grep -n "id:" tree.yaml | head -40
```

你会看到 `agent-loop`、`session-persistence-jsonl`、`tool-bash`……每一条 id 都是本文地图里的一个居民。

**实验 B：找日志文件**

```sh
ls ~/.dsh/sessions/
```

每次对话一个目录，里面是（可选 zstd 压缩的）JSONL 文件——第 04 篇我们就打开它逐行拆解。

## 三原则对账

- **原则一（记一次）**：全程只有一个真相源——三份账本全部派生自同一条日志流；
- **原则二（组合而非修改）**：消息流经的每个关口都是插件行为，适配器、工具、pre-step 监听者无一例外；
- **原则三（不可说谎）**：请求必须等于日志重推结果，输出必须过 schema，协议顺序违反即报错。
