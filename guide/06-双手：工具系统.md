# 06 · 双手：工具系统

> 本篇目标：搞懂 harness 最"工程"的部分——工具的定义、校验、安检、执行、展示与并发调度，以及 DSH 最大胆的一步棋 **Code Mode**：让模型写代码来调用工具。读完你将拥有一个能同时容纳本地工具、MCP 工具和程序化调用的统一工具运行时设计。

## 从一个问题开始

天真版工具系统五分钟就能写完：

```ts
const tools = {
  read_file: async ({ path }) => fs.readFileSync(path, 'utf8'),
  run_bash: async ({ cmd }) => execSync(cmd),
}
// 模型说要用工具 → tools[name](args) → 结果转成字符串塞回消息
```

它在 demo 里无懈可击，在产品里全是洞：

| 问题 | 天真版的下场 |
|---|---|
| 参数校验 | 每个工具手写 `if (!args.path) throw ...`，schema 与实现必然漂移 |
| 结果大小 | `read_file` 读了个 10MB 日志 → 上下文当场爆炸 |
| 权限模型 | 谁说了算这个 agent 能不能跑 bash？写在工具实现里就散了 |
| 取消/超时 | 每个工具自己造轮子，还总忘记 |
| 展示 | UI 想把工具结果显示得好看？去解析字符串吧 |
| 外来工具 | MCP 服务器的工具是另一套协议 → 再造一条执行通道 |

DSH 的答案是**一个大统一**：所有工具——内置的、MCP 来的、甚至一段用户脚本里调用的——都是同一种东西（`ToolDefinition`），都过同一条流水线（九站），都注册在同一个作用域化注册表上。

## ToolDefinition：一只工具的完整身份证

```ts
// packages/core/tools/src/index.ts:222-288（节选）
export interface ToolDefinition extends ToolSchema {      // name/description/parameters
  readonly output: ToolOutputDefinition     // ← 必填！规范输出声明
  execute(args: unknown, exec: ToolRunContext): Promise<unknown>
  finalizeContent?(exec, result): ContentBlock[] | undefined
  timeoutMs?: number            // 仅宿主可见："NEVER sent to the model"
  isConcurrencySafe?(args): boolean   // 并行分类器；非 true 一律视为独占
  presentCall?(args): ToolCallView | undefined        // UI 展示钩子
  presentResult?(args, result): ToolResultView | undefined
}
```

第一眼就该注意到那个必填的 `output`：

```ts
// index.ts:212-219
interface ToolOutputDefinition {
  schema: JsonSchemaNode          // 对成功返回值做 JSON Schema 校验
  render(args, value): ContentBlock[]   // 值 → 给模型看的内容块（纯函数）
  presentationMeta?(args, value)  // 只给顶层调用的 UI 元数据
}
```

这解决了一个几乎所有 harness 都将就的问题：**结果值的形态不再由实现者口头承诺，而是声明+校验+渲染三件套**。执行体返回一个普通 JSON 值，登记表负责照着 schema 验证（违规抛 `INVALID_TOOL_OUTPUT`）、按 render 折算成给模型的块。工具体从此只写业务逻辑，说一不二。

其他字段的克制也值得学：`timeoutMs` 明文注释"绝不发给模型"（它只是宿主策略）；`presentCall/presentResult` 是**软校验**的 UI 钩子——参数不合法就返回 undefined 回退通用卡片而不是抛错，因为 UI 重放旧日志参数时永远不该炸（`defineTool`，`schema.ts:594-609`）。

### defineTool：类型化工厂

第一方工具不手写裸 JSON Schema，走 `packages/core/tools/src/schema.ts:545-617` 的工厂：编译期 DSL → JSON Schema，并把 `execute` 包上一层——**调用用户函数之前先验证参数**，非法即抛 `ToolArgsError('INVALID_ARGS')`。模型的笔误永远到不了你的业务代码。DSL 本身是个封闭联合（string/number/array/object/json/oneOf…），object 必须显式写 `additionalProperties`，required 用每属性注解表达——全部为了让生成出的 schema 与文档严格同源。

## 九站流水线：一次调用的完整旅程

```
模型 tool-call ──▶ ┌─① 物化：mint token·快照冻结参数
                    ├─② code 模式塌缩检查（非 run_code 直接拒绝 UNKNOWN_TOOL）
                    ├─③ tools/pre-execute waterfall（默认放行）——注意：不能改参数！
                    ├─④ 决策 ask → 审批 seam（没装审批服务=deny）
                    ├─⑤ 单调守卫 guard 复查（只有 allow 才评估）
                    ├─⑥ 取消双重检查（审批后·派发前）
                    ├─⑦ tools/execute 环绕层（超时策略住这里）
                    ├─⑧ 工具体 execute → 快照 → output 校验 → render → meta
                    ├─⑨ tools/post-execute（accept 改内容 / block 转反馈）
                    └─▶ finalize + 冻结 + 广播 tools/result
```

逐站拆解最有味道的部分：

**③ pre-execute 不能改参数**。JSDoc 明言 input rewriting 被排除（index.ts:586-588）——理由在于原则一：参数此刻已被记录进日志、展示给用户，改了就是两本账。想改请去上一站之前（根本轮次输入处）。

**④ ask 的降级哲学**。审批不是硬依赖而是机会式消费：没装审批服务、或不在 agent 上下文里，ask 一律降级为 deny（1689-1729 行）；拒绝细分成三种可区分结果（rejected 用户说不 / cancelled 渠道关闭 / unavailable 无渠道）——**模型必须能分清"人拒绝了"还是"没人能回答"**，否则它会错怪用户或傻等。

**⑤ 单调守卫**。guard 类型注释值得原文引用（700-710 行）：*"Because guards have no allow result, listener ordering cannot turn a denial back into permission."* 守卫只能"维持允许"或"追加拒绝"，没有"强制允许"。决策词汇是闭集 `{allow} | {deny} | {ask}`，配合先全局后作用域的求值顺序，**任何插件加载顺序都无法把一次否决翻转成许可**。安全属性不靠纪律靠结构。

**⑦ signal 熔合而非替换**。环绕层 wrapper 可以换信号（超时就是这么实现的，`packages/guard/timeout-policy/src/index.ts:56`），但注册表用 `fuseToolSignals` 把 caller 信号与 wrapper 信号熔合（1889-1916 行）——外层取消权不会被内层吞掉。另有一个状态位 `bodyInvoked` 区分取消发生在派发前（→`ABORTED_BEFORE_DISPATCH` 合成结果对）还是已开始（→正常终化入库），呼应第 03 篇的回放平衡铁律。

**⑨ post-execute 的两种改写**。accept 可以换 content（直接生效）或换 value（换值会重走完整的成功管线——重新校验重新渲染，杜绝绕过 schema）；block 则把"修正性反馈"以 isError 内容回流给模型——工具结果的纠错回路成了流水线的一等公民。（第 13 篇的 spill 插件正是住在这里截胡超大输出。）

## 内置工具全家福与外来户 MCP

权威清单在生成的 `docs/tool-catalog.zh.md`，全景如下：

| 家族 | 工具 | 定义位置 |
|---|---|---|
| 文件 | read / write / edit / read_image | `packages/fs/tool-fs/src/*.ts` |
| 发现 | glob / grep（打包版 ripgrep） | `packages/fs/tool-fs-search/` |
| Shell | bash / pwsh 及其 PTY 持久变体 | `packages/shell/tool-*` |
| 任务 | job_kill/list/output | `packages/jobs/tool-jobs/` |
| 终端 | terminal_open/close/list/read/send/signal | `packages/terminal/tool-terminal/` |
| Web | web_search / web_fetch | `packages/web/tool-web/` |
| LSP | lsp | `packages/lsp/tool-lsp/` |
| 认知 | todo_write / create·get·update_goal / exit_plan_mode / skill / ask_user_question | 各自包 |
| 协作 | subagent / send_message / interrupt_agent / list_agents / report | `packages/subagent/tool-*` |
| 历史 | session_search / session_trace 等 5 个 | `packages/session-query/tool-session-query/` |
| 编排 | workflow / ralph | `packages/workflow/tool-*` |

MCP 服务器接入是最能检验"大统一"成色的案例（`packages/mcp/mcp-client/src/tools.ts`）：每个 server 插件占一个命名空间，公开名确定性派生为 `mcp__<server>__<name>`（超 64 字符则补 12 位 SHA-256 后缀防碰撞）；每次同步两阶段全量替换（拉新列表构建下一代定义→整体 dispose 旧代注册新代，网络错误或撞名则整批保持上一代不动）。关键结论：**产出的就是标准 ToolDefinition**，于是自动获得与本地工具完全一致的九站流水线与提示词投影——统一发生在"定义形状"这一层，不需要任何适配器特判。

并行调度补充一句：exclusive 工具独占批次形成屏障（有意保守，见 `tool-calls.ts` 注释），`maxParallelToolCalls` 支持设置热更新、写入非法值在校验层即拒。

## 压轴创新：Code Mode——让模型写代码调工具

现在把这些铺垫叠起来看 DSH 最大胆的一步。原生 function calling 有个结构性成本：

> N 个动作 = N 个 JSON 编码的请求往返。而且 JSON 里**没法写循环和条件**——"对这 50 个文件各做一次 grep 再汇总"就要模型来回话 50 次。

DSH 的答案：`tools.Config.mode = native | code | both`。切到 `code` 时：

1. **原生 schema 全部从模型请求中撤下**，只留一个保留传输工具 `run_code`（`code-mode.ts:20` 的 `RUN_CODE_NAME`——保留的意思是任何 restriction 删不掉它、同名 scoped 注册也遮不住它）；
2. 提示词换成两段协同声明：order 99 的 code-only 说明（措辞与执行器的拒绝谓词共用同一谓词常量，**prompt 不撒谎**）+ order 150 的 SDK 段——把注册表的工具 schema **纯投影**成 `declare const tools: {...}` 的 TypeScript 声明（或 Python TypedDict），且按发起调用的 scope 现场再生成（删掉 restricted 后的视图与 SDK 承诺严格一致）；
3. 模型写真正的代码：`async 函数体 + await tools.grep({...})`，控制流留在沙箱里跑。

```ts
// 模型实际提交的东西长这样：
const hits = []
for (const f of ['a.ts', 'b.ts', 'c.ts']) {
  const r = await tools.read({ target: f })
  if (r.text.includes('TODO')) hits.push(f)
}
return { hits }
```

**安全与记账怎么保住？** 这是 Code Mode 设计最精彩的部分——程序跑在隔离 worker 里，但每次 `await tools.xxx()` 回调桥接回注册表的**四级分阶段调度接口** `TOOL_RUNTIME_SCHEDULER.prepare/dispatch/finalize/finish`（symbol 私有视图，`index.ts:451-466`）：这正是原生并行调度用的同一套内部 API。于是：

- 子调用拿独立 id `<callId>:code:<n>`，照过 pre-execute/guard/approval/post-execute 全套九站；
- **起点严格按提交顺序**单车道排program起始（日志与策略可预测），**执行体**并发上限默认 10，exclusive 子调用独占并保持屏障到 commit 完成——"exactly like a native exclusive group"；
- 程序立即拿到 resolve 值不等待账目；`tool/code-dispatch(-start)` 日志 append 走旁路 logWork 在 run 结束前排干——**所有子调用的账都在 run_code 自己的轮次里闭合**；
- 执行容器是每次新建的 worker thread，预算四件套：计算 60s / 墙钟 600s / 输出 64MiB / 堆 512MB，`teardown()` 保证 dispose 时每个 worker 强制退稳；
- 错误是结果字段不是异常：六种正交失败 `exception | timeout | abort | worker-exit | invalid-output | output-limit`——预算耗尽≠异常、中止≠超时，分类正交才能精确自愈；
- 绑定对象用 `Object.create(null)` 防 prototype 碰撞；模型失败收到 `CodeRunFailedError` 附带完整捕获输出——沙箱与模型是"敌对但可自纠"的关系。

一句话总结这次压轴：**同一个工具注册表，第三个投影**。原生模式投影成 JSON Schema 数组，Code Mode 投影成 TS SDK 或 Python TypedDict，而策略层完全共享。这就是"词汇先行、边缘翻译"路数的极致复利。

## 三原则对账

| 原则 | 本章证据 |
|---|---|
| 一 · 记一次 | 参数冻结入账后不许改（pre-execute 禁 rewrite）；Code Mode 子调用账目全在原轮次闭合 |
| 二 · 组合 | 决策全靠监听者闭集表决；MCP 以标准定义形状融入；SDK 段按 scope 现场投影 |
| 三 · 不说谎 | guard 结构性单调（排序翻不了案）；output schema 校验拒绝不老实的结果；prompt 措辞与执行谓词同源 |

## 复刻清单

- [ ] `ToolDefinition` + 必填 `output{schema,render}` 三件套；宿主专用字段绝不进模型 schema；
- [ ] `defineTool` 工厂：DSL→JSON Schema，执行前硬校验（INVALID_ARGS）；
- [ ] 九站执行管线：物化冻结 → pre-execute（禁改参）→ ask 降级语义 → 单调 guard → 双重取消检查 → around+signal 熔合 → body+输出校验 → post-execute 改写/阻断 → finalize 广播；
- [ ] 作用域注册表：global 层 + scope 链遮蔽 + restrictions 过滤（自己的注册不受自身过滤）；
- [ ] 一个 MCP 式的外来工具同步器：确定性命名 + 两阶段全量替换；
- [ ] （进阶）run_code 最小版：worker 隔离 + null-proto 绑定 + 分阶段回调桥 + 预算四件套。

验收标准：
1. 两个插件分别 deny 和 allow 同一次调用——无论装载顺序如何，结果是否恒为 deny？
2. 工具体返回不符合自家 output schema 的值——是否当场 INVALID_TOOL_OUTPUT 且未污染日志？
3. code 模式下模型直接点名调用一个被收编的原生工具——是否得到带路径指引的 UNKNOWN_TOOL？

## 超越思考

- **更多语言的三表联动**：TS/Python 已模板化，接 Go/Rust 的 SDK 投影就是复制这套 JSON-Schema↔类型声明的联动法；
- **更细的 partial 沙箱语义**与并发的跨语言子调用拓扑可视化——代码跑起来之后"发生了什么"目前仍主要靠文本日志想象。
