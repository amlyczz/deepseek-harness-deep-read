# 09 · 组装：启动与发行

> 本篇目标：回答两个问题——**`npx @deepseek-ai/dsh web` 敲下回车之后，到一棵运行中的插件树之间发生了什么？以及：一个官方发行的产品，怎么做到"用户可以随意改造而不 fork"？** 读完你将掌握 profile/bundle/patch 三件套的精确机制。

## 从一个问题开始

第 08 篇讲清了"一棵树如何互相连接"，但还欠一个问题：**树上到底挂了谁、按什么顺序、以什么配置？**

这其实是一个发行问题。想象你在负责发布 dsh：

- 内置功能拆成 npm 包，但用户要的是"一键可用"，不能让他自己读文档手动组装 40 个插件；
- 用户想改掉其中三个插件的配置、加自己的两个插件——改包是 fork，迟早烂尾；
- web 版和纯命令行版共享 90% 的功能——再复制一份配置清单吗？

DSH 的答案浓缩成三个名词：

> **bundle（组合包）管"什么和什么在一起"、profile（档案）管"这台机器用哪套组合"、patch（补丁）管"具体哪一条配置改成什么"。三者都是数据，不是代码。**

启动链路全部在两处实现：`apps/cli/src/`（CLI 外壳）与 `packages/boot/app-boot/src/`（引导内核）。

## boot 七步曲

```
npx @deepseek-ai/dsh web
 │
①bin.ts 解析 argv ─────────── launcher 只认识 --profile/--patch/--dump-*，
 │                            第一个陌生 token 之后的一切原样透传给被引导的应用
②分派模式 ── 'profile'(正常启动) | 'plugin'(转发 pnpm) | 'dump-config'
③分层环境快照 loadLayeredEnv ─ 继承环境 > 调用目录 .env > $DSH_HOME/.env；
 │                            .env 里禁止出现 DSH_* 等引导变量（防供应链惊喜）
④composeProfile 组装 patch 栈 ─ 见下一节，产物是一份有序 rows 表
⑤boot() ─ new Context()，baseUrl=profile 目录（相对插件名从这里解析）
 │         ctx.provide('dshHomePath', …)（!!js 表达式的数据源）
⑥mountRootInclude ─ 把 Include 注册为内置插件，创建固定 id='include' 的根行，
 │                   config 携带 cordis.yml 路径与 patches —— Loader 从此接管
⑦await + 启动审计 ─ assertEntriesActivated 报出失败/悬空行；未捕获异常由
                    fail-loud 处理器打一条 stderr 并 exit(1)
```

三处细节值得放大：

**launch 只解析自己的旗标**。`dsh web --port 4000` 里的 `--port` 不是 launcher 认识的参数——它原样传给树上的 web-startup 插件去解析（commander 的 `passThroughOptions`）。webserver 行的配置写着 `port: !!js ctx.webStartup.port ?? 3080`：先问启动服务要端口，没有就 3080。顺带一个妙处：`dsh web --help` 时若无 startup 服务应答，相关行永远 pending——**帮助信息天然不会意外拉起服务器**。

**根配置永远是空的 `[]`**。官方把这一条当作最高纪律（base 补丁文件头注释原文："applied as ONE insert over the empty profile root ... Row order carries no load semantics"，`packages/bundle/base/cordis.patch.yml:1-13`）。树的全部内容都来自 insert+patch 的叠加。而且每次启动都会**重写** profile 的根 yml 为 `[]`——因为 Loader 有写回习惯，不重写的话上次组合出的行会被烤进去，下次启动重复插入。

**fail loud 而不是 fail silent**。悬空的条目、失败的插件在启动审计里点名道姓；unhandledRejection 直接 exit(1)。一个装不齐的 harness 比一个残废的 harness 危险得多。

## patch 栈的层叠顺序

`composeProfile(name, patchFiles)` 产出的完整顺序（从底到顶）：

```
[ ] ← 空根配置（永远）
 ├── 每个组合包的 patch 文件（依 profile 清单顺序）      ← bundle 层
 ├── profile 自己的用户层                                ← $DSH_HOME/profiles/<name>/cordis.patch.yml
 ├── home 级用户层                                       ← $DSH_HOME/cordis.patch.yml（跨 profile 生效）
 ├── 每个 --patch 参数指定的 overlay                      ← 命令行临时层
 ├── shipped 预设根补丁                                   ← 注入 apps/cli/config/agent-presets/
 └── 遥测开关补丁                                         ← env 驱动的最后微调
```

每条 patch 是 YAML 数组里的元素，三种基本操作：

```yaml
- id: agent-default-model          # 按 id 定位既有行……
  config:                          # ……整体替换其 config（不是合并！）
    provider: deepseek-official
    model: deepseek-v4-flash
- id: tool-bash
  disabled: true                   # 或者干脆关掉它
- id: my-cool-tool                 # 或者插入新行（插件名相对 baseUrl 解析）
  name: ./my-cool-plugin
```

注意"替换而非合并"的设计选择：想改一行里十个字段的两个字段？你得整行重写并把另八个也抄上。看似笨拙，实则杜绝了"深层合并撞车"这个 YAML 配置系统的经典灾难源，也让 `--dump-config` 的输出可预测。

**bundle 是什么**：一个普通 npm 包，只是 package.json 里多了一行 `"dsh": {"bundle": {"patch": "./cordis.patch.yml"}}`。profile 通过 manifest 声明叠放哪些：

```jsonc
// $DSH_HOME/profiles/web/package.json
{ "dependencies": { "@deepseek-ai/dsh-base": "…", "@deepseek-ai/dsh-web-app": "…" },
  "dsh": { "profile": { "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app"] } } }
```

base 层装的是"每个模式都需要"的一切：模型适配器、会话持久化、沙箱、工具全家福、压缩家族、审批……（对应第 02 篇地图里的智能平面+能力平面）；web-app 层叠上 HTTP 服务器与浏览器应用；headless 层则叠一次性运行器、完全不带服务器。**每个用户可见的行为调整都属于下面三类之一：改 base 里已有的某行配置（patch）、加新能力（新包）、换模式（换第二个 bundle）。**

## web 与 headless：分叉只在一份数组常量

最惊人的事实藏在 `packages/boot/app-boot/src/profile.ts:114-117`：

```ts
const PROFILE_TEMPLATES = {
  web: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-web-app'],
  headless: ['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-headless'],
}
```

两种模式在**代码层面只有这一个 if**——其余全是数据差异：web 树多出 webserver/api-gateway/connection/web-runtime 等 HTTP 相关行，headless 完全没有；各模式的 startup 插件各自消费透传来的命令行参数；headless 的 runner 行用 `task: !!js ctx.headlessStartup.task` 驱动一次性任务后退出。同一条 runProfile 引导路径跑两种产品。

这也是"一切皆 patch"的最高展示：产品形态本身是发行数据的选择题，不是代码分支的填空题。

## `dsh plugin`：安装即修改发行数据

```sh
dsh plugin --profile web add "github:someone/repo#main"
```

背后发生的事（`apps/cli/src/plugin.ts:120-158`）：

1. profile 目录若不存在先按模板初始化并提示；
2. **spawnSync('pnpm', args, cwd=profile 目录)**——包管理全权交给 pnpm，所以 npm 包/Git 仓库/本地路径/file:/link: 全支持；
3. 成功后 reconcilePlugins：对比安装前后的 dependencies，**凡声明了 `dsh.bundle.patch` 的新依赖自动追加进 profile 的 bundles 清单**；不再声明 bundle 的依赖移出；普通依赖装了也不会激活（没资格进层叠）。对比的是"安装态"而非安装事件，所以 update 触发的变化同样能对账；
4. 一个符号链接农场维护着 `$DSH_HOME/profiles/node_modules` 的依赖闭包（BFS 含 peers），保证任意 profile 都能解析到内置插件，而 in-box 永远优先来自安装位置而非本地拷贝。

生效时机是**下次启动**——刻意不做热激活。理由很理性：bundle 改变的是层的构成，热更层数相当于给飞行的飞机换机翼；组件级热更新（Cordis HMR）已经覆盖了开发期需求，发行态追求确定性。

## 周边三件套速览

- **settings**：单文件 `$DSH_HOME/settings.yaml`，chokidar 监听外部编辑热发布，写入跨进程锁+叶级保注释 diff；
- **credentials**：四层凭证序（继承环境 → `$DSH_HOME/.credentials.yaml` → 项目 `.env` → home `.env`），密钥按请求解析、**从不物化进进程环境变量**——导出 env 排查问题时不会泄漏密钥；
- **agent presets**：含 `agent.cordis.yml` 的目录就是预设，信任级 system/user 分层，shipped 版随发行注入（minimal/standard/code/cordis 四档），坏预设以 broken 标记留在名册而不是悄悄消失。

## `--dump-config`：让系统向你说真话

```sh
npx @deepseek-ai/dsh --profile web --dump-config > tree.yaml
```

输出的 YAML 带 `# == patched by …` 来源注释分组（prefix 快照差分渲染），展示每行配置最终值与被哪些层修过。关键工程原则写在注释里：**dump 与真实挂载调用同一个 composeEntries 函数**（`app-boot/index.ts:350-356`）——不存在"dump 是理论值、实际跑的是另一套"的漂移可能。"打印出来的任何条目都可以被你自己的 patch 替换"，这句 README 承诺由这条工程约束兑现。

## 复刻清单

- [ ] 定义你的 Entry = {id, name(模块路径), config}；root 初始恒为 []；
- [ ] `applyEntryPatches(rows, patches)` 单趟应用：id 替换整份 config / disabled / insert 追加；
- [ ] 三层 patch 栈（内置→项目→用户）+ 最后一层永远是命令行 overlay；
- [ ] 双锚点解析：安装目录优先、本地目录兜底——保证内置包不被同名本地货劫持；
- [ ] 启动审计：缺失依赖、禁用链、加载异常逐条报错退出；
- [ ] dump 与真实装配共用同一函数（这是必须写进测试的架构不变量）；
- [ ] （选做）starter templates 数组驱动的双形态发行。

验收标准：
1. 构造三层 patch 同修一行 id——最终值是否等于最上层的整份 config？
2. 你能否在不改任何包代码的前提下，靠一份用户的 cordis.patch.yml 给产品新增一个端到端功能？
3. dump 输出手动作为配置喂回系统重新启动——是否得到完全相同的树？

## 超越思考

- **重启生效太生硬**：组件级热更新已有，层级变更仍需重启。安全预览模式（dry-run 一棵影子树 diff 后一键切换）也许能把"装插件"的体验带进交互时代；
- **配置的可视化编辑器**：patch 是结构化数据，本就该有 GUI。配合上一章说的运行时树检视器，可以长出"所见即所得的组合包工作台"；
- **信任模型**：目前 bundle 无签名验证（npm 生态自带一点）。对分发第三方组合包的平台，签名与来源审计值得原生内建。
