# 导读：这个系列怎么读

这是《从零看懂 DeepSeek Harness》的导读。花 10 分钟读完它，后面 15 篇每一篇在讲什么、为什么这样排序，你就都清楚了。

## 一、我们从哪里出发

大模型 API 本质上是一个"文本进、文本出"的函数：你发一段消息列表，它回你一段文字，仅此而已。它很聪明，但它**没有手脚**（不能执行命令、不能读写文件）、**没有记忆**（每次请求都得把历史重新喂给它）、**没有感官**（不知道文件改没改、任务跑完没有）、也**没有刹车**（一旦给了它删除文件的权力，谁来拦住它的误操作）。

**Agent harness 就是补齐这四样东西的那层软件**：

```
┌──────────────────────────────────────────────┐
│                 Agent Harness                │
│                                              │
│   手脚 = 工具系统      记忆 = 会话/上下文管理   │
│   感官 = 事件与状态    刹车 = 沙箱与审批        │
│                                              │
│         骨架 = 插件框架（把它们组装起来）        │
└───────────────┬──────────────────────────────┘
                │ 消息进、消息出
        ┌───────▼───────┐
        │   大模型 API   │ ← 它只会这个
        └───────────────┘
```

模型能力各家趋同的今天，**体验差距主要来自 harness**——同一个模型，配上不同的手脚、记忆和刹车，就是完全不同的产品。所以"读懂一个优秀的 harness"是当下性价比最高的学习投资。

我们选的样本是 DeepSeek 官方开源的 **DeepSeek Harness（DSH）**：仓库 `deepseek-ai/deepseek-harness`，MIT 协议，约 54 个子包、近 8000 个源码文件，自带一套罕见地诚实的架构文档。它是这一代 agent harness 里架构野心最大的作品之一，值得逐层拆开看。

## 二、全书的三条主线

拆解过程中你会发现，DSH 所有看似繁杂的设计，其实反复服务于三条非常朴素的工程原则。我把它们提前立在这里，后面每一章都会回头对照——你也可以用它们去审视任何其他 harness：

### 原则一：事实只记录一次，其余皆投影

会发生的事情，只以一种形式、在一个地方被记录下来；模型看到的历史、屏幕上渲染的消息、磁盘上的文件、token 账单……全部从这份唯一的事实源**推导**出来，而不是各存一份。推导过程可以被运行时断言校验（"发给模型的，必须等于从日志重推出来的"），于是整个系统变成了可审计的。

> 这就是 UI 圈常说的 Event Sourcing（事件溯源），DSH 把它用到了 agent 的每一个角落。

### 原则二：扩展靠组合，不靠修改

没有需要打补丁的特权内核。想加一种模型？注册一个适配器。想加一个工具？注册一条工具定义。想拦截每一次请求？监听一个事件。所有注册都是**可逆副作用**——插件卸载时自动撤销，热更新因此成立。支撑这一切的是底层的 Cordis 框架和贯穿全仓的 seam（接缝）模式。

### 原则三：宁可失败，不可说谎

坏参数在入口就拒绝，而不是烂在深处；工具的能力事实会如实反映到给模型的 schema 里（沙箱不存在就不显示"申请提权"字段）；关键不变量不满足时宁可崩溃也不带病运行；错误是有结构的分类词汇，而不是裸字符串。fail-closed（失败即关闭）是这个代码库里出现频率最高的气质。

## 三、15 篇的逻辑地图

全书的展开顺序 = 你亲手造一个 harness 时会遇到的顺序：

```
【宏观】 01 开篇 ………………………… agent/harness 到底是什么
         02 全景 …………………………… 一条消息的一生（先看见全局）

【核心引擎】这三样最小可用的 harness 就该有：
         03 心脏：Agent 循环    ← 先让它转起来
         04 真相：会话日志      ← 让每一次转动都有账可查
         05 出口：LLM 适配层    ← 让它能换任何大脑
         （06 双手：工具系统    ← 让它能干活）
         （07 缰绳：沙箱审批    ← 让它干活不出事）

【骨架形态】核心引擎为什么能长成这样？因为下面这两层：
         08 骨架：Cordis       ← "一切皆插件"的底层机制
         09 组装：启动与发行    ← profile/bundle/patch 组装术
         10 脸面：Web 前端     ← 事件如何变成像素

【认知增强】光有引擎还不够，模型还需要"自我管理"的能力：
         11 分身：Subagent      ← 把活外包出去
         12 自律：记账工具族     ← todo/goal/plan/jobs/schedule
         13 大管家：上下文管理   ← 让对话窗口永不爆掉

【动手超越】
         14 复刻路线图          ← M0~M5 六个里程碑
         15 超越 DSH            ← 弱点清单与创新提案
```

注意一个反直觉的排序：**Cordis 放在第 8 篇而不是第 1 篇**。因为它解决的"插件化"问题，只有在你已经体会过循环/日志/工具这些引擎之后才有体感——先看发动机怎么转，再研究底盘为什么这样设计，比反过来轻松得多。

## 四、每篇的固定结构

为了保证"小白能读懂、工程师能复刻"，除前两篇导览性质外，每篇都是同一个骨架：

| 小节 | 回答的问题 |
|---|---|
| **从一个问题开始** | 这个子系统存在的理由是什么？不做它会怎样？ |
| **天真做法** | 一个新手最自然会怎么写？会踩什么坑？ |
| **DSH 的解法** | 总览图 + 设计意图 |
| **深入细节** | 逐模块拆解，源码摘录 + `file:line` 锚点 |
| **三原则对账** | 本章设计分别服务于哪条主线原则 |
| **复刻清单** | 照着做就能实现同等功能的 checklist |
| **超越思考** | DSH 在这里的局限和你可能的突破口 |

## 五、约定

- 文中路径都相对上游仓库根目录，例如 `packages/core/session/src/index.ts:604` 表示该文件第 604 行；
- 章节里的代码摘录为忠实转录或轻度截取（省略号标注删减），语义不变；
- 阅读前提：任意一门编程语言的基础（最好写过一点 TypeScript/JavaScript），不需要 agent 开发经验；
- 基线版本：上游 main 分支 `0.1.1-rc.2`（2026-08-27 同步）。

准备好了就从 [第 01 篇 · 开篇](./01-开篇：Agent%20Harness%20到底是什么.md) 开始吧。
