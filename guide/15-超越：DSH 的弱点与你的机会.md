# 15 · 超越 DSH：弱点与你的机会

> 本篇目标：全书 15 篇的最后一篇不是总结陈词，而是**出发清单**。前面各章"超越思考"小节已经零散指出过 DSH 的局限，这里把它们集中成一张完整的弱点地图，并给出十个具体的创新提案。看懂 DSH 只算及格；知道它哪里弱、为什么弱、怎么补，才算出师。

## 先摆正心态

DSH 是极优秀的工程，这份清单里没有一条是嘲讽——每一条都伴随它的设计语境（开发预览期优先正确性、组合性优先于性能等）。**每一条弱点同时也常常是某个优点的影子**：串行保守换来了回放保真，先记后判换来了审计完备。超越的正确姿势是识别出"这个取舍在什么条件下不再划算"，然后做出不同的选择。

## 十个创新提案

按投入产出比排序。每个都标注了它替换或修补的是哪个弱点。

### 提案一：内建轮次预算 governor（修 W1）

把 `{maxSteps, maxTokens, maxCostUsd}` 变成 turn 配置并在状态机里原生计数，超限触发一个新增的持久事件 `turn/budget-exceeded`，走关闭协议而非抛异常。关键设计点：计数依据复用 token-meter 折叠值，**不引入第二个真相源**。工作量：一个周末；价值：所有自动化长任务的保险丝。

### 提案二：可撤销收件箱与 dead-letter（修 W2）

claim 决策改为两段式：`reserve()`（标记为已预留但不删除）→ pre-step 表决 → `commit()/return()`。被拒消息进 dead-letter 队列并广播事件，UI 可一键重投。注意死锁窗口与重放兼容性——这正是它值得写成开源插件再反哺上游的原因。

### 提案三：多级取消树（修 W3）

per-step 与 per-tool-call 的 AbortController 层级化，"取消当前步保留后续输入""软取消（让正在跑的工具自然结束）"成为一等语义。复用第 03 篇讲过的合成结果对机制即可保证回放平衡。

### 提案四：精确计量层（修 W6）

在适配器层做增量 tokenizer 缓存（各家的 tokenizer 都有 wasm/纯 JS 实现），fallback 才是密度估算。把 context-window 从"水位警报"升级为"精确仪表 + 预测曲线"，连带解锁提案九。

### 提案五：统一 transport + 结构化错误（修 W7）

抽一个 `httpTransport` 服务统一超时/连接池/重试接线/dns 缓存，错误分类基于 code+cause 而非文本匹配。这同时消掉 DeepSeek 适配器里遗留的 TODO 和 pi-ai 的 XXX。上游自己都想做的事，谁先做好谁就是适配器生态的基础设施。

### 提案六：能力 manifest + 插件权限面板（修 W9）

安装包在 package.json 声明 `dsh.permissions: ["tools.register", "events.on:agent/*", "fs.scope:workspace"]`，宿主加载期校验并在运行时提供权限使用热图（哪些插件最近碰了凭证？）。安全叙事从"信任作者"升级为"审查行为"。与第 09 篇的 dump 机制天然合体。

### 提案七：可视化树工作台（修 W10）

`--dump-config` 已是结构化数据；做一个本地 Web 工作台：实时渲染运行中的插件树（epoch 卡点、依赖等待链）、点击任意行生成对应 patch、diff 预览后应用。这是给整个插件生态开发者修的高速公路，也是最容易出彩的贡献位。

### 提案八：目标验收实证化（修 W13）

goal 增加 `acceptance: {commands[], assertions[]}` 字段，complete 由 harness 实际执行断言判定而非模型自评。与第 12 篇的 jobs/schedule 天然组合："每 N 分钟跑一次验证命令直到绿"。这可能是提升 agent 可信度性价比最高的一刀。

### 提案九：任务经济学层（修 W12 的成本侧）

会话级 cost budget、子代理派生继承额度、自动降档路由（fork→spawn / 旗舰→flash / full context→摘要）。token 在 agent 经济里就是货币，而货币系统不该事后对账，该有央行。

### 提案十：跨 harness 委派协议（更大的棋）

subagent seam 的注释已经预示方向："把一个轮次委派给另一个产品"。标准化一个带权限转移的任务描述符（payload=描述符+种子前缀+能力需求+预算），任何 harness 都能接单。这不是改良 DSH，这是创造 DSH 之上的新网络效应——第 11 篇说过的 fork/spawn 统一，将在协议层面再度上演。

## 一个更深的视角

注意到这些提案的共同点了吗？**没有一条需要 fork DSH。**

这是因为你花了十五章读懂的那个架构本身：循环可以借 turn-stopping 外挂治理、工具可以在 post-execute 加价、压缩可以在 pre-step 接管、前端可以从零另起。"扩展靠组合不靠修改"意味着**改进权不全在设计者手里**——提案一、二、四、六、八都可以作为社区插件实现，用产品本人给留的门打穿它。这是一个系统最高级的开放姿态，也应该是你自己造 harness 时刻进基因的品格。

最后回到导读的三条原则。它们不止解释了 DSH：

1. **事实只记录一次，其余皆投影** —— 你未来遇到任何"两个地方显示的不一样"的 bug，先怀疑有人私建了真相源；
2. **扩展靠组合，不靠修改** —— 未来遇到"改不动了"的系统，先找有没有特权内核；
3. **宁可失败，不可说谎** —— 未来评审任何"静默降级"的设计，先问降级后用户知不知道。

带着这三把尺子和这份弱点地图出发吧。祝你的 harness 比 DSH 更强、更诚实、也更自由。
